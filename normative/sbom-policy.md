# SBOM Policy — Политика учёта компонентов программного обеспечения ASG-TOI

> **Документ:** SBOM Policy для проекта ASG-TOI (Адаптивный
> семантический шлюз — ASG / АСШ).
> **Версия:** 1.0
> **Статус:** утверждено для внутреннего применения в рамках проекта
> ASG-TOI.
> **Основание:** OWASP CycloneDX v1.5; NIST SP 800-218 SSDF;
> Executive Order 14028 (методологическая основа, не применяется
> юрисдикционно); ГОСТ Р 56939-2016 (требования к безопасной
> разработке ПО).
> **Связь с монографией ТОИ:** настоящая Политика является
> практической реализацией положений § 4.7 редакционного заключения
> монографии «Технология интероперабельности», касающихся управления
> зависимостями и контроля целостности программно-аппаратного
> комплекса ASG.

## 1. Назначение и область применения

### 1.1. Назначение

1.1.1. Настоящая Политика устанавливает единые требования к учёту
компонентов программного обеспечения, используемых в проекте
ASG-TOI (далее — Проект), посредством формирования и сопровождения
реестра компонентов программного обеспечения (Software Bill of
Materials, SBOM).

1.1.2. Политика направлена на обеспечение:

- прозрачности состава программного обеспечения ASG (далее — ПО ASG);
- возможности оперативного выявления компонентов, содержащих
  известные уязвимости;
- прослеживаемости происхождения всех компонентов ПО ASG;
- возможности аудита и контроля соответствия требованиям
  лицензионной чистоты и безопасности;
- соответствия требованиям ФЗ-149 «Об информации, информационных
  технологиях и о защите информации», ФЗ-152 «О персональных данных»
  и ГОСТ Р 56939-2016 в части безопасной разработки ПО.

### 1.2. Область применения

1.2.1. Требования настоящей Политики распространяются на:

- исходный код проекта ASG-TOI, размещённый в основном репозитории
  `github.com/smev/asg`;
- все программные зависимости, объявленные в файлах сборки
  (`build.gradle.kts`, `lakefile.lean`, `requirements.txt`,
  `package.json` и т. п.);
- Docker-образы, используемые для упаковки компонентов ASG;
- Helm-чарты и манифесты Kubernetes, описывающие инфраструктуру
  развёртывания ASG;
- конфигурационные файлы, включающие ссылки на внешние образы
  или пакеты.

1.2.2. Требования настоящей Политики обязательны для всех
участников Проекта, включая штатных сотрудников команды ASG и
внешних контрибьюторов.

1.2.3. Требования настоящей Политики не распространяются на:

- компоненты, используемые исключительно для разработки и тестирования
  и не входящие в поставляемый продукт (например, плагины IDE);
- локальные конфигурационные файлы разработчиков, не размещаемые в
  репозитории Проекта.

## 2. Термины и определения

2.1. **SBOM (Software Bill of Materials)** — машиночитаемый реестр
компонентов, используемых в программном обеспечении, оформленный в
формате CycloneDX JSON или CycloneDX XML версии не ниже 1.5,
содержащий сведения о каждом компоненте, его версии, источнике
получения, лицензии и известных уязвимостях.

2.2. **Компонент (component)** — программная единица, включаемая в
состав ПО ASG, в том числе:

- исходная библиотека (например, `org.apache.jena:jena-arq`);
- Docker-образ стороннего производителя (например, `redis:7-alpine`);
- Helm-чарт стороннего репозитория;
- бинарный артефакт, полученный из внешнего репозитория;
- подмодуль исходного кода, разрабатываемый в составе ASG-TOI.

2.3. **Зависимость (dependency)** — отношение между компонентами,
при котором один компонент требует наличия другого для своего
функционирования. Различают:

- **прямую зависимость** — компонент, явно объявленный в файле сборки;
- **транзитивную зависимость** — компонент, привлекаемый через прямую
  зависимость.

2.4. **Уязвимость (vulnerability)** — недостаток в компоненте ПО,
который может быть использован для нарушения конфиденциальности,
целостности или доступности информации, обрабатываемой ПО ASG.
Идентифицируется по системе CVE (Common Vulnerabilities and
Exposures) или эквивалентной.

2.5. **Severity (степень серьёзности уязвимости)** — показатель
серьёзности уязвимости по шкале CVSS v3.1: `Critical` (9.0–10.0),
`High` (7.0–8.9), `Medium` (4.0–6.9), `Low` (0.1–3.9),
`None` (0.0).

2.6. **Artifact registry** — реестр артефактов, используемый для
хранения SBOM, Docker-образов, JAR-файлов и иных артефактов сборки
(в рамках Проекта — GitHub Container Registry с расширением через
GitHub Artifacts и репозиторий Releases).

2.7. **VEX (Vulnerability Exploitability eXchange)** — машиночитаемый
документ, оформленный в формате CycloneDX VEX, содержащий сведения
о возможности эксплуатации выявленных уязвимостей в контексте
конкретного продукта. Формируется при невозможности или
нецелесообразности устранения уязвимости.

2.8. **SLA для устранения уязвимостей** — установленный настоящей
Политикой предельный срок устранения выявленной уязвимости,
исчисляемый с момента её выявления.

## 3. Требования к формированию SBOM

### 3.1. Формат и минимальное содержание SBOM

3.1.1. SBOM формируется в формате CycloneDX JSON версии 1.5 или
выше. Формат CycloneDX XML допускается как дополнительный.

3.1.2. Минимальный набор полей SBOM (в соответствии со спецификацией
CycloneDX 1.5 и NTIA Minimum Elements):

- `bomFormat` — `CycloneDX`;
- `specVersion` — `1.5`;
- `serialNumber` — уникальный идентификатор SBOM (UUID);
- `version` — целочисленный номер версии SBOM;
- `metadata.timestamp` — дата и время формирования SBOM (UTC);
- `metadata.tools` — сведения об инструменте, сформировавшем SBOM;
- `metadata.component` — сведения о продукте ASG, для которого
  сформирован SBOM (`name`, `version`, `type`, `purl`);
- `components` — массив компонентов;
- для каждого компонента: `type`, `name`, `version`, `purl`
  (Package URL), `licenses`, `supplier`, `hashes`.

3.1.3. Для каждого компонента должны быть указаны:

- `purl` — Package URL в соответствии со спецификацией
  `pkg:<type>/<name>@<version>`;
- `licenses` — идентификатор лицензии по SPDX (например, `Apache-2.0`,
  `MIT`, `BUSL-1.1`);
- `supplier` — наименование организации-поставщика компонента;
- `hashes` — криптографические хеши (SHA-256) для проверки
  целостности загружаемого артефакта.

3.1.4. Для каждого компонента должны быть указаны сведения о его
происхождении:

- `evidence` — способ обнаружения компонента (например, анализ
  файла сборки);
- `properties` — дополнительные сведения, включая URL репозитория,
  коммит и дату загрузки.

### 3.2. Автоматическая генерация SBOM в CI

3.2.1. Генерация SBOM осуществляется автоматически в рамках CI/CD
пайплайна ASG-TOI на стадии сборки (см. `.github/workflows/ci.yml`,
блок `sbom-scan`).

3.2.2. Инструмент генерации SBOM — `anchore/sbom-action@v0.16.0`
или эквивалентный, утверждённый командой безопасности ASG.

3.2.3. SBOM формируется для следующих артефактов сборки:

- основного JAR-файла `asg-core` (продукт задачи `shadowJar`);
- Docker-образа `ghcr.io/smev/asg-core:0.1.0`;
- Helm-чарта `asg` (после упаковки `helm package`).

3.2.4. SBOM формируется при каждом:

- релизе (создании тега `v*`);
-merge в ветку `main`;
-merge в ветку `release/*`.

3.2.5. Сформированный SBOM публикуется как GitHub Artifact (для
промежуточных сборок) и как GitHub Release Asset (для релизов).
Имя файла: `sbom-asg-core-<version>.cyclonedx.json`.

3.2.6. Генерация SBOM не должна увеличивать общее время CI-пайплайна
более чем на 5 минут. Время генерации контролируется метрикой
`sbom_generation_duration_seconds` в Prometheus.

### 3.3. Контроль целостности SBOM

3.3.1. Сформированный SBOM подписывается усиленной квалифицированной
электронной подписью ответственного за релиз (для релизных сборок)
или подписью CI-системы GPG (для промежуточных сборок).

3.3.2. Подпись хранится рядом с SBOM в виде файла
`sbom-asg-core-<version>.cyclonedx.json.sig`.

3.3.3. Перед публикацией релиза производится автоматическая
верификация целостности SBOM; в случае расхождения хешей или
невозможности проверки подписи релиз блокируется.

### 3.4. Обновление SBOM при изменении зависимостей

3.4.1. Любое изменение состава зависимостей (через PR, изменяющий
`build.gradle.kts`, `lakefile.lean` или иной файл сборки) должно
сопровождаться обновлением SBOM в том же PR.

3.4.2. CI-пайплайн автоматически проверяет соответствие SBOM в PR
актуальному составу зависимостей. В случае расхождения PR
блокируется до устранения несоответствия.

3.4.3. Автоматическое обновление зависимостей (через Dependabot или
Renovate) разрешено только для патч-обновлений (`patch`-level).
Минорные и мажорные обновления требуют ручного анализа и согласования
с командой безопасности ASG.

## 4. Хранение и доступ к SBOM

### 4.1. Хранение SBOM

4.1.1. Все сформированные SBOM хранятся в GitHub Container Registry
как OCI-артефакты с тегом, соответствующим версии ASG.

4.1.2. Срок хранения SBOM для релизных версий ASG — не менее 5 лет
с даты релиза.

4.1.3. Срок хранения SBOM для промежуточных сборок (snapshot) —
не менее 90 дней с даты сборки.

4.1.4. По истечении срока хранения SBOM удаляется автоматически.
Перед удалением производится архивирование в защищённое хранилище
(Vault-Backup) с сохранением в течение дополнительных 3 лет.

### 4.2. Доступ к SBOM

4.2.1. Доступ к SBOM релизных версий ASG предоставляется:

- команде разработки ASG — на чтение;
- команде безопасности ASG — на чтение и запись метаданных;
- аудиторам — на чтение по запросу;
- внешним потребителям ASG — на чтение через публичный интерфейс
  (раздел «Releases» репозитория `github.com/smev/asg`).

4.2.2. Доступ к SBOM промежуточных сборок предоставляется только
команде разработки ASG и команде безопасности ASG.

4.2.3. Доступ к архивным копиям SBOM (Vault-Backup) предоставляется
исключительно по запросу команды безопасности ASG с обязательным
фиксацией факта доступа в журнале аудита.

### 4.3. Публикация SBOM

4.3.1. При публикации релиза ASG SBOM автоматически публикуется как
часть релизных артефактов и сопровождается VEX-документом, если в
составе SBOM выявлены неисправленные уязвимости.

4.3.2. Публикация SBOM для промежуточных сборок не производится.
Доступ к таким SBOM осуществляется по запросу через CI-систему.

4.3.3. SBOM, формируемый для публичных релизов ASG, должен
соответствовать требованиям NTIA Minimum Elements for an SBOM и
спецификации CycloneDX 1.5.

## 5. Управление уязвимостями

### 5.1. Автоматическое сканирование уязвимостей

5.1.1. Сканирование SBOM на наличие известных уязвимостей
осуществляется автоматически на следующих стадиях:

- при формировании SBOM в CI/CD пайплайне;
- ежедневно по расписанию (cron) для всех актуальных релизных SBOM;
- при появлении новых записей в NVD (National Vulnerability
  Database) — в течение 24 часов с момента появления записи.

5.1.2. Инструмент сканирования — `aquasec/trivy-action@v0.20.0`
или эквивалентный, утверждённый командой безопасности ASG.

5.1.3. Источники данных о уязвимостях:

- NVD (National Vulnerability Database);
- GitHub Advisory Database;
- OSV (Open Source Vulnerabilities);
- собственная база уязвимостей ASG (для внутренних компонентов).

5.1.4. Результаты сканирования автоматически публикуются в GitHub
Security tab и направляются команде безопасности ASG через
уведомления Slack (канал `#asg-security`).

### 5.2. Пороги серьёзности и SLA для устранения

5.2.1. Для выявленных уязвимостей устанавливаются следующие пороги
серьёзности и SLA для их устранения:

| Severity       | CVSS v3.1 | Действие                                   | SLA           |
|----------------|-----------|--------------------------------------------|---------------|
| Critical       | 9.0–10.0  | Блокировка релиза; устранение обязательно  | 7 дней        |
| High           | 7.0–8.9   | Блокировка релиза; устранение обязательно  | 30 дней       |
| Medium         | 4.0–6.9   | Уведомление; устранение желательно         | 90 дней       |
| Low            | 0.1–3.9   | Уведомление; устранение по возможности     | без обязательства |
| None           | 0.0       | Без действий                               | не применимо  |

5.2.2. При выявлении уязвимостей со статусом Critical или High в
релизной версии ASG команда безопасности ASG обязана в течение
24 часов сформировать VEX-документ, содержащий оценку возможности
эксплуатации уязвимости в контексте ASG, и принять одно из решений:

- устранить уязвимость в установленный SLA;
- выпустить обновлённый релиз ASG с устранённой уязвимостью;
- опубликовать mitigation (рекомендации по снижению рисков);

5.2.3. Решение о выпуске ASG с неисправленной уязвимостью со статусом
Critical или High может быть принято только:

- при наличии VEX-документа, обосновывающего невозможность
  эксплуатации уязвимости в контексте ASG;
- при согласовании с владельцем продукта ASG и командой безопасности
  ASG;
- при документировании решения в журнале аудита.

5.2.4. В случае выявления уязвимостей со статусом Critical или High
в released-версии ASG, находящейся в эксплуатации, команда
безопасности ASG обязана в течение 7 дней уведомить потребителей
ASG через выпуск Security Advisory в репозитории
`github.com/smev/asg/security/advisories`.

### 5.3. Анализ транзитивных зависимостей

5.3.1. Управление уязвимостями распространяется на все компоненты
SBOM, включая транзитивные зависимости.

5.3.2. В случае выявления уязвимости в транзитивной зависимости,
устранение осуществляется путём:

- обновления версии прямой зависимости, использующей уязвимую
  транзитивную;
- замены прямой зависимости на альтернативную, не использующую
  уязвимую транзитивную;
- при невозможности вышеуказанного — обращения к разработчику
  прямой зависимости с просьбой обновления;
- при невозможности вышеуказанного — формирования VEX-документа с
  обоснованием невозможности эксплуатации уязвимости в контексте ASG.

### 5.4. License Compliance

5.4.1. SBOM должен содержать сведения о лицензии каждого компонента
(поле `licenses`).

5.4.2. Запрещается использование в составе ASG компонентов с
лицензиями, несовместимыми с Apache License 2.0, в частности:

- GPL-2.0-only, GPL-3.0-only (для библиотек, линкуемых статически);
- AGPL-3.0-only (для любого способа линковки);
- лицензии, не одобренные OSI.

5.4.3. Использование компонентов с лицензией BUSL-1.1 допускается
при условии соблюдения условий лицензии, в том числе — при
соответствии даты использования требованиям Change Date. Команда
безопасности ASG обязана ежегодно проверять соблюдение условий
лицензий BUSL-1.1 для всех используемых компонентов.

5.4.4. Автоматическая проверка совместимости лицензий
осуществляется инструментом ` fossology/fossology` или эквивалентным
на стадии CI. В случае выявления несоответствия PR блокируется.

## 6. Аудит и контроль соответствия

### 6.1. Регулярный аудит SBOM

6.1.1. Команда безопасности ASG проводит ежеквартальный аудит SBOM
на соответствие требованиям настоящей Политики.

6.1.2. В рамках аудита проверяется:

- наличие SBOM для всех актуальных релизных версий ASG;
- корректность формирования SBOM (соответствие формату CycloneDX
  1.5, заполнение обязательных полей);
- соответствие SBOM фактическому составу зависимостей;
- наличие подписей и их корректность;
- наличие актуальных результатов сканирования уязвимостей;
- соблюдение SLA для устранения уязвимостей;
- соблюдение требований лицензионной чистоты.

6.1.3. Результаты аудита оформляются актом, утверждаемым владельцем
продукта ASG. Акт хранится не менее 5 лет.

### 6.2. Аудит при релизе

6.2.1. Перед каждым релизом ASG команда безопасности ASG проводит
предрелизный аудит, включающий:

- проверку актуальности SBOM;
- проверку отсутствия неисправленных уязвимостей со статусом
  Critical и High без VEX-обоснования;
- проверку лицензионной чистоты компонентов.

6.2.2. Релиз ASG не может быть выпущен без успешного прохождения
предрелизного аудита. Решение об отклонении от этого правила
принимается владельцем продукта ASG и фиксируется в журнале аудита.

### 6.3. Отчётность

6.3.1. Команда безопасности ASG ежемесячно представляет владельцу
продукта ASG отчёт, содержащий:

- количество выявленных уязвимостей по уровням серьёзности;
- количество устранённых уязвимостей в установленный SLA;
- количество просроченных SLA и причины просрочки;
- количество компонентов с лицензиями, требующими повышенного
  внимания (BUSL-1.1 и др.);
- сведения о проведённых аудитах.

6.3.2. Ежегодный отчёт о соблюдении настоящей Политики
включается в годовой отчёт о безопасности ASG и представляется
руководству организации.

## 7. Роли и обязанности

### 7.1. Владелец продукта ASG

7.1.1. Утверждает настоящую Политику и вносимые в неё изменения.

7.1.2. Принимает решение об отступлении от требований настоящей
Политики в случаях, предусмотренных разделом 5.

7.1.3. Обеспечивает выделение ресурсов, необходимых для реализации
требований настоящей Политики.

### 7.2. Команда безопасности ASG

7.2.1. Осуществляет контроль соблюдения требований настоящей
Политики.

7.2.2. Проводит аудит SBOM в соответствии с разделом 6.

7.2.3. Принимает решения об устранении выявленных уязвимостей или
формировании VEX-документов.

7.2.4. Утверждает инструменты генерации и сканирования SBOM.

7.2.5. Представляет отчётность в соответствии с разделом 6.

### 7.3. Команда разработки ASG

7.3.1. Обеспечивает автоматическую генерацию SBOM в CI/CD пайплайне.

7.3.2. Обновляет SBOM при изменении состава зависимостей.

7.3.3. Устраняет выявленные уязвимости в установленные SLA.

7.3.4. Соблюдает требования лицензионной чистоты компонентов.

### 7.4. Ответственный за релиз ASG

7.4.1. Подписывает релизные SBOM усиленной квалифицированной
электронной подписью.

7.4.2. Обеспечивает публикацию SBOM и VEX-документов при выпуске
релиза.

7.4.3. Принимает решение о блокировке релиза при выявлении
критических уязвимостей.

### 7.5. Контрибьюторы

7.5.1. Соблюдают требования настоящей Политики при внесении
изменений в состав зависимостей.

7.5.2. Обновляют SBOM в PR, изменяющем состав зависимостей.

7.5.3. Своевременно устраняют выявленные в их PR уязвимости.

## 8. Ссылочные документы

### 8.1. Международные и национальные нормативные документы

8.1.1. **NTIA — Minimum Elements for a Software Bill of Materials
(SBOM)**, 2021. — Базовые требования к составу SBOM.

8.1.2. **NIST SP 800-218 — Secure Software Development Framework
(SSDF) Version 1.1**, 2022. — Рекомендации по безопасной разработке
ПО.

8.1.3. **Executive Order 14028 — Improving the Nation's
Cybersecurity**, 2021. — Используется как методологическая основа
(не применяется юрисдикционно к проекту ASG-TOI).

8.1.4. **CycloneDX Specification v1.5**, OWASP Foundation, 2023. —
Спецификация формата SBOM, используемого в проекте.

8.1.5. **OWASP — CycloneDX Tool Center**, https://cyclonedx.org.
— Справочник инструментов для работы с CycloneDX.

8.1.6. **ГОСТ Р 56939-2016** «Защита информации. Разработка
безопасного программного обеспечения». — Требования к безопасной
разработке ПО в Российской Федерации.

8.1.7. **ФЗ-149** «Об информации, информационных технологиях и о
защите информации». — Базовые требования к обработке информации в
Российской Федерации.

8.1.8. **ФЗ-152** «О персональных данных». — Требования к защите
персональных данных, влияющие на состав и хранение SBOM.

### 8.2. Внутренние документы ASG-TOI

8.2.1. **`docs/security.md`** — Документация по безопасности ASG,
включая описание RBAC, JWT-аутентификации и NetworkPolicies.

8.2.2. **`docs/CONTRIBUTING.md`** — Руководство для контрибьюторов,
включая требования к PR и составу зависимостей.

8.2.3. **`.github/workflows/ci.yml`** — CI/CD-пайплайн ASG,
включающий стадии `sbom-scan` и `trivy-scan`.

8.2.4. **`asg-core/build.gradle.kts`** — Файл сборки основного
компонента ASG, определяющий состав прямых зависимостей.

8.2.5. **`CHANGELOG.md`** — Журнал изменений ASG, в котором
фиксируются сведения об обновлениях зависимостей и устранённых
уязвимостях.

### 8.3. Связь с монографией ТОИ

8.3.1. Настоящая Политика является практической реализацией
положений § 4.7 редакционного заключения монографии «Технология
интероперабельности» (ТОИ), касающихся:

- управления зависимостями программно-аппаратного комплекса ASG;
- контроля целостности программно-аппаратных средств
  интероперабельности;
- прослеживаемости происхождения данных и программных компонентов.

8.3.2. Опыт применения настоящей Политики в проекте ASG-TOI
должен быть обобщён в отдельном приложении к монографии ТОИ в
будущих редакциях.
